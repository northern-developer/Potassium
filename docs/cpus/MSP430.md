# MSP430 target notes

`machines/MSP430.json` is a deliberately small slice of TI's MSP430: just the
instructions E4.T3's ELFCLASS32 test program needs
(`examples/MSP430.asm`, `tests/link/program.c` compiled by
`clang --target=msp430 -O1`). It exists to check ptasm's 32-bit ELF writer
against LLVM's tools, not as an MSP430 assembler. The rest of the
instruction set is on the wish list (`plan/wishlist.md`).

---

## 1. References

- TI's *MSP430x1xx/2xx/4xx Family User's Guide*, CPU chapter
  (instruction formats, addressing modes, constant generator).

## 2. Machine

16 registers (`R0` = PC, `R1` = SP, `R2` = SR, `R3` = constant generator,
`R4`-`R15` general), 16-bit addresses, little-endian. Instructions are
16-bit words, plus one extension word per immediate or address operand.

ELF: `ELFCLASS32`, `e_machine` 105 (`EM_MSP430`), RELA relocations, as
clang writes them. One relocation type: `"addr16": 5`
(`R_MSP430_16_BYTE`). `relOffset` is `"after"`, for `JNE`.

## 3. Instructions

| ptasm | MSP430 | Encoding | Notes |
|---|---|---|---|
| `MOV Rn, imm` / `MOV Rn, label` | `mov #imm, rN` | `0x403N`, then the 16-bit word | the source is `@PC+` (As = 11, register PC): the word after the opcode |
| `CALL label` | `call #target` | `0x12B0`, then the 16-bit target | an **absolute** address, so even a call to a local label is a relocation |
| `RET` | `ret` (`mov @SP+, PC`) | `0x4130` | a fixed word |
| `PUSH Rn` | `push rN` | `0x120N` | |
| `POP Rn` | `pop rN` (`mov @SP+, rN`) | `0x413N` | its own fixed encoding: no autoincrement mode needed |
| `MOV Rd, Rs` | `mov rS, rD` | `0x4000`, source in bits 11-8, destination in bits 3-0 | register-direct both sides |
| `INC [label]` | `inc &label` (`add #1, &label`) | `0x5392`, then the 16-bit address | `&` is written as `[ ]` |
| `AND Rn, imm` | `and #imm, rN` | `0xF03N`, then the 16-bit word | |
| `CMP Rn, imm` | `cmp #imm, rN` | `0x903N`, then the 16-bit word | |
| `JNE label` | `jne label` | `0x2000` + a signed 10-bit offset in **words** from the next instruction (`valueLsb: 1`) | a label in the same section; ptasm doesn't relax it |

ptasm writes MSP430 code in its own Intel syntax, destination first
(`MOV R12, 1`); MSP430's own syntax is source first (`mov #1, r12`).

## 4. Examples

- `examples/MSP430.asm`: `tests/link/program.c` as clang compiles it,
  with each hand edit marked `; ptasm:`.
- `examples/MSP430-negative.asm`: what the positive one avoids -- an
  absolute section at the start of flash (`.ORG 0xC000`) with a `JNE`
  back to its label (a negative word offset) -- and two errors that need
  `-w`: an unknown mnemonic and a missing form.

## 5. Known gaps

- clang encodes `mov #1, r12`, `cmp #1, r10` and `clr r15` in one word
  through the constant generator (R3, As = 01); `machines/MSP430.json` has
  only the long form, so those instructions are a word longer than clang's
  (`examples/MSP430.asm` marks them). The constant generator, the
  autoincrement mode and the rest of the instruction set are on the wish
  list.

## 6. How it's tested

`ctest`'s `link-msp430` (`tests/cmake/link_check.cmake` mode `msp430`, registered when clang
targets MSP430): assemble the example with `-f elf`, compile
`tests/link/main.c` freestanding with clang, link both with `ld.lld`
(`--image-base=0x4000`: the default base is above 16 bits), and check the
linked pointer table holds the addresses of `str0`, `str1` and `str2 + 4`.
clang's own object for `tests/link/program.c` must give a table of the same
shape. Nothing here can run MSP430 code, so the resolved relocations are
the test.
